# Project Docs

## Description

自动分析项目，生成或同步更新包含行为准则、场景化导航的 AGENTS.md 及配套子文档；也可单独或随文档任务一并生成 README.md 与 docs/API_REFERENCE.md。无需额外参数，对话中直接激活即可；未配置命令入口，不承诺命令行调用。

支持三种模式，按 Step 0 判定：

- **单产物模式**：用户只要求编写某个扩展产物（README、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md、API 参考文档），未涉及 AGENTS.md / docs 体系；只生成请求的产物，不创建基线文档，也不触发档位判定。
- **初始化模式**：项目尚无 AGENTS.md，或用户明确要求从零建立文档体系。
- **更新模式**：已有 AGENTS.md，且项目结构、技术栈、架构或规范发生变化，需同步修订文档。只增量调整受影响部分，不重写未变更内容。

## 执行权限与影响范围

- 需要：读取项目文件与目录、读取现有 AGENTS.md 与 docs/ 子文档、在根目录写入 AGENTS.md、在 docs/ 下创建/写入子文档
- 需要（按档位/按需）：在根目录写入 README.md、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md，在 docs/ 下写入 API_REFERENCE.md，仅当用户明确要求或画像档位触发时
- 需要（仅限文档范围）：删除或重命名 docs/ 下由本技能维护的失效子文档；删除前确定待删清单，交付摘要中说明删除结果；不删除源码
- 不需要：安装依赖、修改源码、修改 package.json 等配置文件、提交 Git
- 一律以当前项目的最新实际状态为准：文档内容与现状不符时直接按现状修订，不询问覆盖还是合并
- 已有 AGENTS.md 或 docs 子文档：更新模式下保留未受影响的章节，只改差异部分；过时或失效的文档可删除或重命名，处理结果写入交付摘要
- 权限或工具不可用时按"常见问题与处理"降级，不中途猜测内容填充

## Instructions

1. 判定模式：按模板 Step 0 区分单产物、初始化、更新三种模式，无法判断时向用户提问
2. 分析项目：读取配置文件和目录结构，识别技术栈与架构特点；更新模式额外读取现有文档并列出变更差异清单
3. 生成或更新文档：按模板 Step 2–5 执行，初始化输出全套文档，更新模式只改受影响文件与章节，单产物模式只生成请求的扩展产物
4. 检查并交付：按模板 Step 6 自检，通过后按"输出要求"输出文件列表与文档内容，更新模式附变更摘要

下文提到的 Step 均指 Prompt Template 内的步骤编号。边界情况与降级处理见下方"边界情况""常见问题与处理"两节。

## 工具能力

本技能执行依赖以下工具能力，环境中需可用：

- **文件读取**：读取项目配置文件（package.json、go.mod 等）与源码特征
- **目录扫描**：列举项目目录结构，识别模块划分
- **文件写入**：创建 AGENTS.md、docs/ 下的子文档；按档位创建 README.md、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md 与 docs/API_REFERENCE.md
- **内容检索**：按需搜索源码中的开发规范与约定

## 边界情况

按以下顺序判断是否命中，命中后只基于可确认的事实生成，不推断：

- **无法识别技术栈**（无 package.json / go.mod 等配置文件）：只基于可确认的信息生成文档；技术栈与命令章节留空，不写猜测内容，并把缺失信息作为问题清单交用户补充。
- **配置文件缺失或项目极简**（如单文件脚本）：只生成基线文档（AGENTS.md + docs/PROJECT.md），不生成动态文档；CLI 参数等简短信息合并进 docs/PROJECT.md。
- **特殊项目结构**（monorepo、多包仓库、无标准布局）：先确认包/root 边界，按包边界拆分文档；无法确定根与子项目关系时，向用户提问后再生成。
- **复杂项目**（多技术栈、模块众多、规范分散）：基线文档照常生成；动态文档只覆盖已确认的高价值领域，其余在交付时列出"建议后续补充"，不强行穷举。
- **用户补充说明与文档冲突**：以用户明确说明为准，并在文档中标注该条来源为用户说明。
- **更新模式下现有文档与实际结构严重不符**（大量目录/模块已变）：直接按当前实际结构重新生成对应文档，不以旧文档为基线；无需询问用户，交付时说明已重写的文档及原因。
- **更新模式下变更无法确认**（用户只说"更新一下"但未指出变更点）：以当前实际结构为准，逐项对比现有文档，凡与事实不符之处直接修订，修订范围以差异清单为限，不等待用户确认。

## 常见问题与处理

- **某配置文件读取失败**：跳过该文件，改用目录结构与源码特征判断；仍不足则归入"无法识别技术栈"处理，不阻塞整体生成。
- **目录扫描结果过大或不完整**：限制在根目录及一级子目录，聚焦配置文件、入口文件、规范文件；不递归到依赖目录。
- **更新模式误判为初始化**：检查现有文档是否被整体重写；一旦发生，回退到现有文档，改按变更差异清单做增量修订。
- **更新后章节重复或矛盾**（旧内容未删净）：按差异清单逐项定位新旧描述，删除过时表述，保留最新事实，再执行 Step 6 自检。

## 扩展产物（可选）

仅在用户明确要求或命中 L3 档位时生成。随文档任务交付时不改变基线文档；单产物模式下只生成请求的产物：

- **README.md**：面向人类使用者，控制在 120 行内，必需章节优先，超出时压缩目录与技术栈细节。共用必需内容：一句话定位、前置要求（运行时/包管理器版本）、快速开始（安装/构建/运行，命令必须来自配置文件）、配置与环境变量、测试命令、目录与技术栈简述、指向 AGENTS.md 与 docs/ 的入口、贡献与许可（项目缺失时注明未提供）。类型特有内容按仓库类型补入：库补最小用法示例、导出面、兼容矩阵与版本策略，应用补部署与访问方式，CLI 补命令清单、参数示例与退出码，详见 references/profiles.md"README 类型差异"。定位无法从代码或现有文档确认时向用户提问；禁止营销套话，禁止编造未实现的功能。
- **docs/API_REFERENCE.md**：面向接口调用方，不受子文档 200 行限制。仅当能从路由定义、OpenAPI/Swagger 或请求封装中确认接口时生成；已有 OpenAPI 时以规范为唯一事实源。开头声明契约来源（OpenAPI 文件路径与版本，或路由定义位置），再写 base URL、API 版本、认证方式、Content-Type、统一错误模型，最后按接口列出路径、方法、参数（区分 path/query/body/header）、请求与响应示例、错误码；分页/限流/幂等仅在接口定义中确认时写。无法确认的接口列入问题清单，不猜测。
- **其余产物**：CONTRIBUTING.md、SECURITY.md、CHANGELOG.md 的内容要点见 references/profiles.md"档位文档要点"；单产物模式下按这些要点生成，不套用其他产物的章节。
- **职责区分**：接口约定文档（如 docs/api-conventions.md）保留请求封装与错误处理约定，API_REFERENCE.md 是逐接口参考，两者不合并、不互相替代。
- **更新模式**：扩展产物按变更差异清单增量修订，规则与主文档一致；删除失效接口条目时同步在交付摘要说明。

## 仓库画像与文档档位

生成前先判画像：仓库类型（CLI/库/应用/monorepo）、档位（L1 精简 / L2 团队 / L3 对外）、接口是否公开。默认 L1，命中团队或对外信号才升级；用户指定档位优先，信号冲突或无法确认时按 L1 并在交付摘要说明可升级项。判定信号、各档文档清单、README/API 类型差异见 `references/profiles.md`。

## Prompt Template

当创建具体项目的文档时，使用以下提示词模板：

```markdown
你是项目文档规划专家。请为当前项目设计或同步更新一套面向人类与 AI 的文档体系。

## 项目信息
【从项目文件中自动分析获取】

## 任务要求

请按以下步骤设计：

### Step 0: 判定运行模式
- 用户只要求某个扩展产物（README、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md、API 参考文档），未涉及 AGENTS.md / docs 体系 → 单产物模式，跳过基线与动态文档，不做档位判定；内容规则见"扩展产物（可选）"与 references/profiles.md
- 项目无 AGENTS.md，或用户明确要求从零建立 → 初始化模式
- 项目已有 AGENTS.md，且用户提到结构/技术栈/架构/规范变更或要求同步文档 → 更新模式
- 以上都不明确 → 向用户提问，不自行假定

更新模式下先读取 AGENTS.md 与 docs/ 下全部现有文档作为基线，再进入 Step 1；单产物模式直接进入 Step 1，只读取与目标产物相关的文件。

### Step 1: 分析项目特点
识别技术栈、架构模式、项目结构、开发规范和常用场景。

检测顺序：项目配置文件 → 目录结构 → 源码特征。

更新模式须额外产出"变更差异清单"，逐项列出：
- 技术栈/依赖变化（版本升级、框架替换、新增或移除依赖）
- 目录与模块变化（新增、删除、重命名、移动）
- 命令与配置变化（脚本、构建方式、环境变量）
- 规范与架构变化（约定、分层、数据流）

差异清单只列已确认的事实，作为后续修订的唯一依据；未变化部分不纳入清单。

无法识别技术栈或遇到特殊结构时，按本技能"边界情况"一节处理；不确定信息向用户提问，不在文档中标注"待确认"。

### Step 2: 确定文档结构
固定基线（初始化/更新模式必有；单产物模式跳过）：
1. AGENTS.md（主索引）: 行为准则 + 技术栈概览 + 场景导航 + 常用命令
2. docs/PROJECT.md: 技术栈、目录结构、架构模式

动态文档：根据 Step 1 分析结果，按 Step 3 判断逻辑决定是否拆分。

档位：初始化/更新模式按"仓库画像与文档档位"判定 L1/L2/L3；单产物模式跳过。L1 只生成基线与领域文档，L2/L3 按 references/profiles.md 的清单补齐，不擅自升级。

扩展产物：仅当用户明确要求或命中 L3 档位时，按本技能"扩展产物（可选）"一节生成 README.md 与 docs/API_REFERENCE.md，不作为基线要求。

判断原则：某个领域在项目中有足够的独立复杂度，AI 工作时需要单独查阅该领域的信息，则生成独立文档；否则合并到 docs/PROJECT.md。

### Step 3: 根据项目特点设计场景化文档
单产物模式跳过本步，直接执行 Step 5 的扩展产物部分。

基于 Step 1 的分析结果，识别项目需要的文档：

1. 回顾 Step 1 发现的项目特征（目录结构、技术栈、架构模式）
2. 对每个特征领域判断：是否有足够的独立复杂度值得独立文档？
   - 是 → 生成独立文档，文档名反映领域含义
   - 否 → 相关内容合并到 docs/PROJECT.md
3. 根据实际生成的文档构建场景导航表：只收录 docs/ 下的文档（含生成时的 API_REFERENCE.md）；README.md 面向人类，不进入导航表

更新模式按变更差异清单处理已有文档：
- 领域对应的事实未变 → 文档保留，只修正导航入口，不重写内容
- 领域内容部分变化 → 只修订受影响章节，其余章节原样保留
- 领域已不存在（对应目录/模块删除） → 直接删除或合并对应文档，并同步移除导航条目
- 现有 AGENTS.md 的行为准则与 Step 4 原文不一致 → 用 Step 4 原文整体替换该章节，视为受影响章节
- 新领域复杂度达标 → 新增独立文档并加入导航；不达标 → 并入 docs/PROJECT.md

判断示例（展示推理过程，非固定映射）：
- "项目有组件目录且组件间有复用关系" → 组件规范复杂度够，独立为 COMPONENT.md
- "项目有数据层但只有2个简单表" → 数据模型复杂度不够，写入 docs/PROJECT.md 即可
- "项目是单文件脚本" → 只生成 AGENTS.md + docs/PROJECT.md，不新增其他子文档

### Step 4: 定义行为准则

单产物模式跳过本步：不生成 AGENTS.md，无需嵌入行为准则。

以下内容必须原样嵌入 AGENTS.md，不可省略、不可改写。

 > ## 行为准则
 >
 > ### 1. Think Before Coding
 > **不假设、不隐藏困惑、展示权衡。**
 > - 开发前先读项目文档，了解结构、规范和约束
 > - 按场景导航表按需定位文档，只读任务相关的，不一次性读完
 > - 先按文档执行，未覆盖时再搜索代码/查阅资料
 > - 不确定时先问，不要猜测
 > - 存在多种理解时，列出所有可能
 > - 有更简单的方案就提出来
 > - 搞不明白就停下来，说清楚哪里不明白
 >
 > ### 2. Simplicity First
 > **最小代码解决问题，不做推测性设计。**
 > - 不做需求范围外的功能
 > - 单次使用的代码不做抽象
 > - 没要求的"灵活性"和"可配置性"不加
 > - 不为不可能的场景写错误处理
 > - 避免重复：相同逻辑出现 2+ 次时考虑抽象，说明取舍
 >
 > ### 3. Surgical Changes
 > **只改必须改的，清理自己制造的混乱。**
 > - 不"顺手优化"周边无关代码
 > - 不重构没坏的东西
 > - 遵循现有风格，即使你不认同
 > - 发现无关死代码提出来，不删
 >
 > ### 4. Goal-Driven Execution
 > **定义成功标准，循环验证。**
 > - "加验证" → "先想清楚什么叫通过，再实现"
 > - "修bug" → "先找到最小复现路径，再修复"
 > - "重构X" → "确保行为不变，可用 diff 辅助验证"
 > - 多步任务列出计划：1. [步骤] → verify: [检查]

### Step 5: 编写文档内容

单产物模式只执行"扩展产物"一条，不生成 AGENTS.md、docs/PROJECT.md 与动态子文档。

- AGENTS.md: 行为准则（按 Step 4 原文） + 技术栈概览 + 场景导航表 + 常用命令 + 测试方式（命令与关键测试目录） + 精简注意事项；L2+ 补代码风格与安全边界，使用 PR 流程时补分支/提交/评审要求
- docs/PROJECT.md: 技术栈、目录结构、架构模式 + 不够独立文档的领域章节
- 动态子文档: 仅在 Step 3 判断需要独立时生成；L1 写规范要点 + 注意事项，L2+ 至少补 1 个示例（正例或反例）与检查清单
- 档位文档: L2 生成 CONTRIBUTING.md；L3 在 L2 基础上再加 README.md、SECURITY.md、CHANGELOG.md、docs/API_REFERENCE.md（有 API 时），内容规则见"扩展产物（可选）"与 references/profiles.md
- 扩展产物: 仅在用户明确要求或 L3 档位时生成，内容规则见本技能"扩展产物（可选）"一节
- 更新模式: 以现有文档为基线做增量修订，写入范围限于 Step 3 判定的受影响文件与章节；未受影响章节保持原文，不用模板重新生成

### Step 6: 生成后自检

写入完成后逐项核对，任一项不通过则修正后重新核对。多项冲突时按以下优先级取舍：事实一致 > 准则完整性 > 导航有效性 > 更新增量性 > 档位合规 > 扩展产物合规 > 篇幅限制。

- 文件存在性：文件清单中的每个文件都已实际写入，路径与清单一致
- 导航有效性（生成 AGENTS.md 时）：场景导航表每条目标文件都存在，无空链接、无指向不存在文件的条目
- 准则完整性（生成 AGENTS.md 时）：行为准则四节与 Step 4 原文逐字一致，未省略、未改写
- 篇幅合规（生成文档时）：新建或重写的 AGENTS.md 在 80-120 行（L2 团队档可到 140 行），子文档单文件不超过 200 行（API_REFERENCE.md 除外）；更新模式下未变章节不计入，不为满足行数改写原文
- 事实一致：文档中的技术栈、命令、目录结构均来自项目实际文件，无推断填充
- 更新模式增量性：变更差异清单中的每一项都已在对应文档体现，未变化的章节与原文逐字一致，无重写、无内容丢失
- 扩展产物合规（仅生成时）：README 覆盖定位/前置要求/配置/测试/许可，命令均来自配置文件；API 参考声明契约来源与认证方式，路径/方法/参数/响应与实际接口一致，无编造内容
- 档位合规（初始化/更新模式）：生成清单与判定档位一致，未遗漏档位文档；升级/降级依据已写入交付摘要
```
