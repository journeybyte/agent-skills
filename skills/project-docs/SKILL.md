# Project Docs

## Description

自动分析项目，生成或同步更新包含行为准则、场景化导航的 AGENTS.md 及配套子文档；也可单独或随文档任务生成 README、API 参考、CONTRIBUTING、SECURITY、CHANGELOG。无需额外参数，对话中直接激活即可；未配置命令入口，不承诺命令行调用。

支持三种模式，判定规则见 Prompt Template Step 0，常见触发说法速查见 `references/quickref.md`：

- **单产物模式**：只要求编写某个扩展产物（README、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md、API 参考文档），未涉及 AGENTS.md / docs 体系；只生成请求的产物，不创建基线文档，不做档位判定。
- **初始化模式**：项目尚无 AGENTS.md；或用户对已有文档体系显式要求"从零重建/覆盖/重新生成"（整体重写，先履行保真义务）。
- **更新模式**：已有 AGENTS.md 且项目发生变化；只增量修订受影响部分，不重写未变更内容。已有 AGENTS.md 时的"初始化/整理/补全"类请求默认按本模式处理。

## 执行权限与影响范围

- 需要：读取项目文件与目录、读取现有 AGENTS.md 与 docs/ 子文档、在根目录写入 AGENTS.md、在 docs/ 下创建/写入子文档；monorepo 时在确认的包目录下创建/写入子文档
- 需要（按档位/按需）：在根目录写入 README.md、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md，在 docs/ 下写入 API_REFERENCE.md，仅当用户明确要求或画像档位触发时
- 需要（仅限文档范围）：删除或重命名 docs/（含 monorepo 包内 docs/）下由本技能维护的失效子文档；删除前确定待删清单，按"反馈格式"第 2 项的 `[已删除]` 说明；不删除源码
- 不需要：安装依赖、修改源码、修改 package.json 等配置文件、提交 Git
- 一律以当前项目的最新实际状态为准：文档内容与现状不符（可从代码或项目结构验证）时直接按现状修订，不询问覆盖还是合并；无法从代码验证的事实按"保真义务"处理
- **保真义务**：现有 AGENTS.md 与 docs/ 子文档一律作为信息源读取：仅存于现有文档、无法从代码确认的事实（手写规范、架构决策等）迁移进新文档；无法判断是否仍有效时向用户确认，不静默丢弃
- 已有 AGENTS.md 或 docs 子文档：更新模式下保留未受影响的章节，只改差异部分；过时或失效的文档可删除或重命名，处理结果按"反馈格式"第 2、3 项写入
- 权限或工具不可用时按"常见问题与处理"降级，标 `[降级]` 注记并按"反馈格式"第 5 项写原因，不中途猜测内容填充

## Instructions

1. 判定模式：按模板 Step 0 区分单产物、初始化、更新三种模式，无法判断时向用户提问
2. 分析项目：读取配置文件和目录结构，识别技术栈与架构特点；更新模式额外读取现有文档并列出变更差异清单
3. 生成或更新文档：按模板 Step 2–5 执行，初始化输出全套文档，更新模式只改受影响文件与章节，单产物模式只生成请求的扩展产物
4. 检查并交付：按模板 Step 6 自检，通过后按"输出要求"输出文件列表与文档内容，并按"反馈格式"输出交付摘要

下文提到的 Step 均指 Prompt Template 内的步骤编号。边界情况与降级处理见"边界情况""常见问题与处理"两节；所有对外反馈按"反馈格式"输出。

## 工具能力

本技能执行依赖以下工具能力，环境中需可用：

- **文件读取**：读取项目配置文件（package.json、go.mod 等）与源码特征
- **目录扫描**：列举项目目录结构，识别模块划分
- **文件写入**：创建 AGENTS.md、docs/ 下的子文档，以及 monorepo 确认包目录下的子文档；按档位创建 README.md、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md 与 docs/API_REFERENCE.md
- **内容检索**：按需搜索源码中的开发规范与约定

读取或扫描失败时先自动重试一次（不预判是否瞬时错误），仍失败按"常见问题与处理"降级，不要求用户手动补充文件。

## 边界情况

逐条核对，命中即按该条处理，多条命中时同时适用；一律只基于可确认的事实生成，不推断：

- **无法识别技术栈**（无 package.json / go.mod 等配置文件）：只基于可确认的信息生成文档；技术栈与命令章节留空，不写猜测内容，缺失信息按"反馈格式"的附表列给用户。
- **配置文件缺失或项目极简**（如单文件脚本）：只生成基线文档（AGENTS.md + docs/PROJECT.md），不生成动态文档；CLI 参数等简短信息合并进 docs/PROJECT.md。
- **特殊项目结构**（monorepo、多包仓库、无标准布局）：先确认包/root 边界，按包边界拆分文档，各包文档就近存放，根导航表收录各包文档；无法确定根与子项目关系时，向用户提问后再生成。
- **复杂项目**（多技术栈、模块众多、规范分散）：基线文档照常生成；动态文档只覆盖固定映射表命中的领域，其余按"反馈格式"第 5 项列"建议后续补充"，不强行穷举。
- **用户补充说明与文档冲突**：以用户明确说明为准，并在文档中标注该条来源为用户说明。
- **更新模式下现有文档与实际结构严重不符**（大量目录/模块已变）：直接按当前实际结构重新生成对应文档，不以旧文档为基线（仅存于旧文档的事实仍按"保真义务"迁移或确认）；无需询问用户，重写文件标 `[重写]` 并按"反馈格式"第 4 项说明原因。
- **更新模式下变更点无法确认**（用户只说"更新一下"但未指出变更点；模式已判定为更新，不再就变更点向用户提问）：以当前实际结构为准，逐项对比现有文档，凡与事实不符之处直接修订，修订范围以差异清单为限，不等待用户确认。

## 常见问题与处理

- **某配置文件读取失败**：先自动重试一次；仍失败则跳过该文件，改用目录结构与源码特征判断；再不足归入"无法识别技术栈"处理，不阻塞整体生成，也不要求用户手动补文件。
- **目录扫描结果过大或不完整**：限制在根目录及一级子目录，聚焦配置文件、入口文件、规范文件；不递归到依赖目录。
- **更新模式误判为初始化**：检查现有文档是否被整体重写；一旦发生，回退到现有文档，改按变更差异清单做增量修订。
- **更新后章节重复或矛盾**（旧内容未删净）：按差异清单逐项定位新旧描述，删除过时表述，保留最新事实，再执行 Step 6 自检。

## 反馈格式

所有异常、降级与交付反馈按 `references/feedback.md` 输出：问题清单附表、6 项交付摘要（单产物只输出第 2、6 项）、固定状态前缀。首次交付前读取该文件，不自行改格式。

## 扩展产物（可选）

仅在用户明确要求或命中 L3 档位时生成。随文档任务交付时不改变基线文档；单产物模式下只生成请求的产物：

- **README.md**：面向人类使用者，控制在 120 行内，必需章节优先，超出时压缩目录与技术栈细节。共用必需内容：一句话定位、前置要求（运行时/包管理器版本）、快速开始（安装/构建/运行，命令必须来自配置文件）、配置与环境变量、测试命令、目录与技术栈简述、文档入口（AGENTS.md 与 docs/ 存在时指向，不存在时省略该入口并列入问题清单，不得创建基线文档或写死链接）、贡献与许可（项目缺失时注明未提供）。类型特有内容按仓库类型补入：库补最小用法示例、导出面、兼容矩阵与版本策略，应用补部署与访问方式，CLI 补命令清单、参数示例与退出码，详见 references/profiles.md"README 类型差异"。定位无法从代码或现有文档确认时向用户提问；禁止营销套话，禁止编造未实现的功能。
- **docs/API_REFERENCE.md**：面向接口调用方，不受子文档 200 行限制。仅当能从路由定义、OpenAPI/Swagger 或请求封装中确认接口时生成；已有 OpenAPI 时以规范为唯一事实源。开头声明契约来源（OpenAPI 文件路径与版本，或路由定义位置），再写 base URL、API 版本、认证方式、Content-Type、统一错误模型，最后按接口列出路径、方法、参数（区分 path/query/body/header）、请求与响应示例、错误码；分页/限流/幂等仅在接口定义中确认时写。无法确认的接口列入问题清单，不猜测。
- **其余产物**：CONTRIBUTING.md、SECURITY.md、CHANGELOG.md 的内容要点见 references/profiles.md"档位文档要点"；单产物模式下按这些要点生成，不套用其他产物的章节。
- **职责区分**：接口约定文档（如 docs/API_CONVENTIONS.md）保留请求封装与错误处理约定，API_REFERENCE.md 是逐接口参考，两者不合并、不互相替代。
- **更新模式**：扩展产物按变更差异清单增量修订，规则与主文档一致；删除失效接口条目时按"反馈格式"第 2 项标 `[已删除]`。

## 仓库画像与文档档位

生成前先判画像：仓库类型（CLI/库/应用/monorepo）、档位（L1 精简 / L2 团队 / L3 对外）、接口是否公开。默认 L1，命中团队或对外信号才升级；用户指定档位优先，信号冲突或无法确认时按 L1 并按"反馈格式"第 1 项写可升级项。判定信号、各档文档清单、README/API 类型差异见 `references/profiles.md`。档位判定只依据可确认信号，一次判定后全程沿用，不在运行中反复升级或降级。

## Prompt Template

当创建具体项目的文档时，使用以下提示词模板：

```markdown
你是项目文档规划专家。请为当前项目设计或同步更新一套面向人类与 AI 的文档体系。

## 项目信息
【从项目文件中自动分析获取】

## 任务要求

请按以下步骤设计：

### Step 0: 判定运行模式
- 用户只要求某个扩展产物（README、CONTRIBUTING.md、SECURITY.md、CHANGELOG.md、API 参考文档），未涉及 AGENTS.md / docs 体系 → 单产物模式，跳过基线与动态文档，不做档位判定；内容规则见"扩展产物（可选）"与 references/profiles.md
- 项目无 AGENTS.md → 初始化模式
- 项目已有 AGENTS.md，用户提到结构/技术栈/架构/规范变更、要求同步文档，或提出"初始化/整理/补全"类请求但未显式要求重建 → 更新模式；"初始化"类请求按更新处理时在交付摘要第 1 项注明
- 项目已有 AGENTS.md，用户明确要求"从零重建/覆盖/重新生成" → 初始化模式（重写）：先读取现有文档履行保真义务，再整体重写，重写文件标 `[重写]`；不在新生成集合内的旧子文档视为失效，删除并按"反馈格式"第 2 项标 `[已删除]`
- 以上都不明确 → 向用户提问，不自行假定

更新模式与重写式初始化先读取 AGENTS.md 与 docs/ 下全部现有文档再进入 Step 1：更新模式作为修订基线，重写式初始化作为事实信息源（仅存于旧文档的内容迁移或向用户确认）；尚无文档的初始化与单产物模式直接进入 Step 1，单产物只读取与目标产物相关的文件。

### Step 1: 分析项目特点
识别技术栈、架构模式、项目结构、开发规范和常用场景。

检测顺序：项目配置文件 → 目录结构 → 源码特征。

更新模式须额外产出"变更差异清单"，逐项列出：
- 技术栈/依赖变化（版本升级、框架替换、新增或移除依赖）
- 目录与模块变化（新增、删除、重命名、移动）
- 命令与配置变化（脚本、构建方式、环境变量）
- 规范与架构变化（约定、分层、数据流）

差异清单只列已确认的事实，作为后续修订的唯一依据；未变化部分不纳入清单。

无法识别技术栈或遇到特殊结构时，按本技能"边界情况"一节处理；不确定信息向用户提问，不在文档中标注"待确认"。

### Step 2: 确定文档结构
固定基线（初始化/更新模式必有；单产物模式跳过）：
1. AGENTS.md（主索引）: 行为准则 + 技术栈概览 + 场景导航 + 常用命令
2. docs/PROJECT.md: 技术栈、目录结构、架构模式

动态文档：根据 Step 1 分析结果，按 Step 3 判断逻辑决定是否拆分。

档位：初始化/更新模式按"仓库画像与文档档位"判定 L1/L2/L3；单产物模式跳过。L1 只生成基线与领域文档，L2/L3 按 references/profiles.md 的清单补齐，不擅自升级。

扩展产物：仅当用户明确要求或命中 L3 档位时，按本技能"扩展产物（可选）"一节生成 README.md 与 docs/API_REFERENCE.md，不作为基线要求。

判断原则：动态文档只按 Step 3 固定映射表命中生成——表内条目按给定判定依据（含明确阈值）逐条核对，不额外引入"复杂度是否足够"的主观评估；未命中领域并入 docs/PROJECT.md。

### Step 3: 根据项目特点设计场景化文档
单产物模式跳过本步，直接执行 Step 5 的扩展产物部分。

基于 Step 1 的分析结果，识别项目需要的文档：

1. 回顾 Step 1 发现的项目特征（目录结构、技术栈、架构模式）
2. 对照下方固定映射表逐条核对判定依据（含阈值）：满足即按表中固定文档名生成；未命中任何条目 → 内容并入 docs/PROJECT.md，不另建文档
3. 根据实际生成的文档构建场景导航表：收录 docs/ 下的文档（含生成时的 API_REFERENCE.md）；monorepo 按包边界就近存放的子文档也纳入导航，路径写实际相对路径；README.md 面向人类，不进入导航表

更新模式按变更差异清单处理已有文档：
- 领域对应的事实未变 → 文档保留，只修正导航入口，不重写内容
- 领域内容部分变化 → 只修订受影响章节，其余章节原样保留
- 领域已不存在（对应目录/模块删除） → 直接删除或合并对应文档，并同步移除导航条目
- 现有 AGENTS.md 的行为准则与 Step 4 原文不一致 → 用 Step 4 原文整体替换该章节，视为受影响章节
- 新领域命中固定映射表 → 新增独立文档并加入导航；未命中 → 并入 docs/PROJECT.md

固定映射表（逐条核对判定依据，单一仓库内同一领域只生成一次，不重复拆分）：

| 领域特征 | 固定文档名（UPPER_SNAKE_CASE.md） | 判定依据（来自 Step 1 事实） |
|---|---|---|
| 组件/模块复用 | `COMPONENT.md` | 存在组件/模块目录，且组件间有导入或复用关系 |
| 接口请求约定 | `API_CONVENTIONS.md` | 存在请求封装或统一错误处理模块 |
| 跨模块架构决策 | `ARCHITECTURE.md` | 存在分层、数据流或跨模块调用约定 |
| 数据模型 | `DATA_MODEL.md` | 存在数据层且模型/表 ≥ 3 个 |
| 数据校验 | `VALIDATION.md` | 存在独立校验模块或规则 ≥ 3 条 |
| 单文件极简脚本 | 不新增子文档 | 无子目录、无标准布局 |

固定文档名即命名白名单，统一使用 UPPER_SNAKE_CASE.md：单词全大写，多词用下划线连接；根目录特殊文件 README/AGENTS/CONTRIBUTING/SECURITY/CHANGELOG 同样大写。大小写冲突按以下优先级执行：

1. 新建文档：严格使用表中写法，不改大小写、不改分隔符。
2. 更新已有文档：若既有文件名与表中某项仅大小写/分隔符不同（如 `component.md` 对应 `COMPONENT.md`），视为命中白名单，沿用既有文件名，不改名、不新建。
3. 领域不在表中：并入 `docs/PROJECT.md`，不自造文件名。
4. 用户明确要求新增表外领域：允许新建，文件名用 UPPER_SNAKE_CASE.md，并在交付摘要第 1 项标注"用户指定领域"；未明确要求时按第 3 条处理。

monorepo 例外：判定为 monorepo 时，固定映射表按包边界分别执行——每个包可有同名领域文档（如各包自己的 `COMPONENT.md`），就近存放在包目录下，不受"同一领域只生成一次"限制；包级概览统一写 `<package>/docs/PROJECT.md`，根 `docs/PROJECT.md` 只保留总览与各包链接；根级 AGENTS.md 的场景导航表收录各包子文档，路径写实际相对路径。包边界无法确认时按"边界情况"向用户提问，不猜测拆分。

### Step 4: 定义行为准则

单产物模式跳过本步：不生成 AGENTS.md，无需嵌入行为准则。

以下内容必须原样嵌入 AGENTS.md，不可省略、不可改写。

 > ## 行为准则
 >
 > ### 1. Think Before Coding
 > **不假设、不隐藏困惑、展示权衡。**
 > - 开发前先读项目文档，了解结构、规范和约束
 > - 按场景导航表按需定位文档，只读任务相关的，不一次性读完
 > - 先按文档执行，未覆盖时再搜索代码/查阅资料
 > - 不确定时先问，不要猜测
 > - 存在多种理解时，列出所有可能
 > - 有更简单的方案就提出来
 > - 搞不明白就停下来，说清楚哪里不明白
 >
 > ### 2. Simplicity First
 > **最小代码解决问题，不做推测性设计。**
 > - 不做需求范围外的功能
 > - 单次使用的代码不做抽象
 > - 没要求的"灵活性"和"可配置性"不加
 > - 不为不可能的场景写错误处理
 > - 避免重复：相同逻辑出现 2+ 次时考虑抽象，说明取舍
 >
 > ### 3. Surgical Changes
 > **只改必须改的，清理自己制造的混乱。**
 > - 不"顺手优化"周边无关代码
 > - 不重构没坏的东西
 > - 遵循现有风格，即使你不认同
 > - 发现无关死代码提出来，不删
 >
 > ### 4. Goal-Driven Execution
 > **定义成功标准，循环验证。**
 > - "加验证" → "先想清楚什么叫通过，再实现"
 > - "修bug" → "先找到最小复现路径，再修复"
 > - "重构X" → "确保行为不变，可用 diff 辅助验证"
 > - 多步任务列出计划：1. [步骤] → verify: [检查]

### Step 5: 编写文档内容

单产物模式只执行"扩展产物"一条，不生成 AGENTS.md、docs/PROJECT.md 与动态子文档。

- AGENTS.md: 按以下固定骨架生成，章节顺序固定、内容按 Step 4 与 Step 1 事实填充，不以篇幅为由增删章节：
  1. 行为准则（Step 4 原文，四节齐全）
  2. 技术栈概览（框架/语言/包管理器/关键依赖）
  3. 场景导航表（收录实际存在的文档：根 docs/ 子文档，以及 monorepo 确认包目录下就近存放的子文档；路径写相对根目录的实际路径）
  4. 常用命令（来自配置文件）
  5. 测试方式（命令 + 关键测试目录）
  6. 精简注意事项
  L2+ 在第 6 节内补代码风格与安全边界；使用 PR 流程时补分支/提交/评审要求。
- docs/PROJECT.md: 技术栈、目录结构、架构模式 + 不够独立文档的领域章节
- 动态子文档: 仅在 Step 3 判断需要独立时生成；L1 写规范要点 + 注意事项，L2+ 至少补 1 个示例（正例或反例）与检查清单
- 档位文档: L2 生成 CONTRIBUTING.md；L3 在 L2 基础上再加 README.md、SECURITY.md、CHANGELOG.md、docs/API_REFERENCE.md（有 API 时），内容规则见"扩展产物（可选）"与 references/profiles.md
- 扩展产物: 仅在用户明确要求或 L3 档位时生成，内容规则见本技能"扩展产物（可选）"一节
- 更新模式: 以现有文档为基线做增量修订，写入范围限于 Step 3 判定的受影响文件与章节；未受影响章节保持原文，不用模板重新生成

### Step 6: 生成后自检

写入完成后逐项核对，任一项不通过则修正后重新核对。多项冲突时按以下优先级取舍：事实一致 > 准则完整性 > 导航有效性 > 更新增量性 > 档位合规 > 扩展产物合规 > 篇幅参考。

- 文件存在性：文件清单中的每个文件都已实际写入，路径与清单一致
- 导航有效性（生成 AGENTS.md 时）：场景导航表每条目标文件都存在，无空链接、无指向不存在文件的条目
- 准则完整性（生成 AGENTS.md 时）：行为准则四节与 Step 4 原文逐字一致，未省略、未改写
- 篇幅参考（生成文档时）：按"格式要求"的篇幅规则核对；AGENTS.md 行数为参考值不作硬性条件，硬限仅子文档 200 行（API_REFERENCE.md 除外）
- 事实一致：文档中的技术栈、命令、目录结构均来自项目实际文件，无推断填充
- 更新模式增量性：变更差异清单中的每一项都已在对应文档体现，未变化的章节与原文逐字一致，无重写、无内容丢失；整体重写的文件除外（须标 `[重写]` 并在交付摘要第 4 项说明）
- 扩展产物合规（仅生成时）：README 覆盖定位/前置要求/配置/测试/许可，命令均来自配置文件；API 参考声明契约来源与认证方式，路径/方法/参数/响应与实际接口一致，无编造内容
- 档位合规（初始化/更新模式）：生成清单与判定档位一致，未遗漏档位文档；触发依据与未生成升级项已写入交付摘要第 1 项
- 反馈格式合规：交付摘要按 references/feedback.md 输出，初始化/更新 6 项齐全，单产物仅第 2、6 项，状态前缀合法

自检通过后输出文件列表与文档内容；初始化/更新模式均按"反馈格式"的 6 项模板输出交付摘要，单产物模式只输出第 2、6 项。未通过时先修正，不做"待补充"式交付。

## 输出要求

1. 先输出文件列表，区分固定基线、动态文档、档位文档和扩展产物；初始化/更新模式标注档位与触发依据，单产物模式标注产物类型；初始化/更新模式用"反馈格式"的固定状态前缀标注每个文件（[未动]/[修订]/[新增]/[已删除]/[重写]；[降级] 作注记）
2. 编写每个文档的核心内容；更新模式下未动文件不重复输出全文，只列路径
3. 动态文档命名、导航一致性、篇幅与准则完整性分别按 Step 3 规则与 Step 6 自检执行，此处不重复
4. 不默认生成 ADR、docs 索引或按项目类型拆分的 README 模板；用户明确要求时再补

## 格式要求

- 新建或重写的 AGENTS.md 以 80-120 行（L2 团队档可到 140 行）为参考值，不作硬性通过条件；优先保证固定骨架齐全，不为凑行数增删内容；更新模式未变章节不受此限
- 子文档单文件不超过 200 行（API_REFERENCE.md 除外）
- 文档语言跟随项目现有文档与 README；无现有文档时使用用户当前语言
- 使用 Markdown 表格做导航
- 注意事项精简为要点列表，不展开说明
- **禁止套话**：不要"本文档将介绍..."等开头，直接写内容
- **只写必要信息**：规范、约束、关键路径，不写显而易见的内容
- 代码示例仅限必要场景，优先用描述说明规范
```
